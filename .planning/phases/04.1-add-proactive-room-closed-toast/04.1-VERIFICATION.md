**Conclusion:** the delivery mechanism (`broadcast_to_room` → `getRoomSockets` → per-socket `send`)

`size === 0` never has a real recipient; `size === 1` does.

### Gaps Summary

The fix is well-built at the code level — the broadcast mechanism, the ordering/exclusion logic, the
wire-schema addition, and the web toast mapping are all present, substantive, and correctly wired to
each other. Typecheck and both test suites (154/154 backend, 85/85 web) pass clean, with zero
regressions.

But the phase's actual goal — "proactively push a 'room closed' notification to any other
still-connected client viewing that room... so they see the toast within ~5s — not only reactively on
their next failed action" — is not achieved yet, because the broadcast is hooked to the
`room.players.size === 0` transition, which by construction never has a real recipient: whoever's
departure causes the room to hit zero is, by the ordering fix, correctly excluded from their own notice,
and nobody else can still be registered for that room at that instant (`ClientManager.roomMembers`
tracks room.players 1:1). I confirmed this with an in-memory harness reusing the real `RoomManager` +
`ClientManager` + `bindBridgeToGateway` wiring across 2-player, 3-player, and disconnect-then-evict
scenarios — zero recipients every time at `size === 0`.

The good news, also confirmed by the harness: the same room state one transition earlier
(`room.players.size === 1`, i.e. the second-to-last player just left and exactly one player remains) DOES
have a real, live, reachable recipient — `getRoomSockets(code)` returns the remaining player's socket
directly, no new recipient-tracking mechanism needed. This makes the closure a retargeted hook plus one
product decision (toast copy and room-teardown timing at size===1), not a new architectural feature. See
gap #1's `missing` for the concrete steps.

The regression test added (`rooms.test.ts` #9) does not catch any of this: it only asserts the
engine-side bridge event fires, without registering a second socket or asserting a live recipient, so it
passes regardless of whether the fix actually reaches anyone and would not catch a retargeted-but-wrong
hook either. A ClientManager-level test (gap #2) is needed to make this regression-proof going forward.
