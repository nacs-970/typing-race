# Phase 1 — Plan 02: Prod Static Serving + Dev Proxy Polish (REQ-12)

<objective>
Replace the Plan 01 dev-only static shim with Hono `serveStatic` from `hono/bun` so that in production a single Bun process serves the built React SPA (`apps/web/dist/*`) including the SPA fallback to `index.html` and precompressed `.gz`/`.br` siblings. Wire `vite-plugin-compression` into the Vite build to emit those siblings. Confirm the dev proxy (`/api`, `/ws`) and prod single-process both work end-to-end — both modes must be independently demoable. Harden the Bun.serve WS handler with the production knobs from RESEARCH.md (`idleTimeout: 120`, `maxPayloadLength: 16 KB`, `backpressureLimit: 1 MB`, `sendPings: true`, `perMessageDeflate: true`).

Purpose: REQ-12 says "Fly.io single-process deploy" — frontend + WS API must live in one Bun process and one port. This plan proves it. Without precompressed serving, every asset is uncompressed on the wire — measurable cold-load regression on first paint. Without `idleTimeout`/`maxPayloadLength`, the server is vulnerable to the trivial DoS in RESEARCH.md Known-Gotchas. This plan locks the production WS knobs and proves single-process demo locally (no Fly needed yet — Phase 6 deploys).

Output:
- `apps/server/src/static.ts` rewritten with `serveStatic` for `/assets/*` (long cache, immutable) and SPA fallback (no cache, must revalidate)
- `apps/web/vite.config.ts` adds `vite-plugin-compression` (gzip + brotli)
- `apps/server/src/index.ts` WS handler hardened with production knobs; `fetch` handler branches `NODE_ENV === "production"` to static vs dev shim
- Independent demoability verified: `bun run dev` (Vite on :5173 + Bun on :8080 with WS proxy) AND `bun run build` then `bun run start` (Bun on :8080 serving SPA + WS + /health from one process)
</objective>
