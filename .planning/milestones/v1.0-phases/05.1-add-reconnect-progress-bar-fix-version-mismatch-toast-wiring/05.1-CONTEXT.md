# Phase 05.1 Context: Add reconnect progress bar, fix version-mismatch toast wiring

**Inserted after Phase 5** to close two gaps found by automated
goal-backward verification during v1.0 milestone close
(05-VERIFICATION.md, gsd-verifier).

## Diagnosed gaps (no discuss-phase needed — root cause and fix location already known)

ROADMAP.md Phase 5 Success Criterion 4 requires: "Disconnect shows
'Reconnecting… (5s)' progress bar; reconnect success restores prior view;
reconnect failure shows distinct toast ('Lost connection — room lost' vs
'Server restarted')."

**Gap 1 — reconnect progress bar missing entirely.** No component in
`apps/web/src` reads `useConnectionStore().status` to render a
reconnect-in-progress UI. `GraceBanner` is a different feature (race-finish
grace period, not reconnect). The "disconnected, waiting up to 60s" toast in
`App.tsx` is Phase 4's *other-player-disconnect* notice (shown to
opponents), not the local client's own reconnect progress indicator.

**Gap 2 — version-mismatch toast claimed but not wired.**
`05-04-SUMMARY.md` claims a 4-case error toast set including version
mismatch, but no `VERSION_MISMATCH` error code exists anywhere in
`packages/shared/src/messages.ts` or server code. `ToastQueue.test.tsx`
"proves" this by calling `addToast()` directly with a hardcoded string — a
fixture-only test that never exercises a real production error path. The
roadmap's own Success Criterion 4 only names 2 toast cases (lost
connection / server restarted), both of which ARE correctly wired — so this
is a SUMMARY-level overclaim, not a roadmap miss. Decide whether to (a)
actually wire a real `VERSION_MISMATCH` server→client error path if version
skew is a real risk in this deploy model, or (b) remove the
unwired/fixture-only toast case and correct the SUMMARY's claim. Prefer (b)
unless a concrete version-skew scenario exists (this project has no
independently-versioned client/server release process — check before
building unneeded infra).

## Required fix

1. Add a local-client "Reconnecting… (Ns)" progress bar, driven by
   `useConnectionStore().status` (or equivalent), shown while the client's
   own connection is attempting to recover — distinct from the existing
   opponent-facing "X disconnected" toast.
2. Resolve the version-mismatch toast gap per option (a) or (b) above,
   whichever is the smaller true fix — document the choice in the
   PLAN/SUMMARY.

## Success criteria

- A visible reconnect progress indicator exists and is tested (component
  test or equivalent) driven by real connection-status state, not just
  claimed in a SUMMARY.
- Version-mismatch toast claim in docs/tests matches what's actually wired
  in production code — no fixture-only test asserting an unreachable path.
- No regression in existing engine/gateway/web test suites.
