### Direct code inspection (task items 1 and 4)

**Item 1 — synchronous ordering.** Confirmed by direct read of `apps/gateway/src/index.ts:125-133`:
```ts
const drain = async (timeoutMs = 90_000) => {
  if (drainPromise) return drainPromise;
  drainPromise = (async () => {
    manager.setDraining(true);
    manager.markOwnDrainStarted();   // synchronous, before any await
    if (engineWorker && engineWorker.drain) {
      await engineWorker.drain(timeoutMs);   // first await is here
```
`setDraining(true)` and `markOwnDrainStarted()` execute on the same synchronous tick, before the function's first `await` — no interleaving of any bridge event is possible between them (single-threaded JS, no microtask yield until the first `await`). Confirmed in `apps/gateway/src/ws/handlers.ts:112-114` that the `"drained"` handler's reset is gated on `!manager.hasOwnDrainStarted()`, exactly as claimed.

**Item 4 — remaining race analysis.** No race causes mis-attribution of the flag itself:
- Because `markOwnDrainStarted()` fires synchronously at the very start of the gateway's own `drain()`, `ownDrainStarted` is `true` for the entire duration of the gateway's own cycle, with zero window where an interleaved event could see it as `false`.
- An unrelated `"drained"` arriving *after* `markOwnDrainStarted()` (during the gateway's own async wait) is correctly *not* used to reset `draining`, because the gateway is genuinely mid-shutdown at that point — draining should stay `true` regardless of which cycle's event triggered the check. No mis-attribution in this direction.
- A **different**, pre-existing race does exist and is unrelated to 06.1: in the split-mode branch (`index.ts:149-169`), a stray `"drained"` from a *concurrent, unrelated* engine cycle (not a *stale* one — `onShutdown`'s `setDrained(false)` only guards against staleness) can resolve `eventPromise` early and cut the gateway's own wait short. `06-REVIEW-FIX.md` already acknowledged this exact tradeoff when it fixed CR-B1's `drained` latch; 06.1 does not introduce or worsen it, and it is out of 06.1's stated scope (draining-latch reset, not drain-wait-early-resolution). Documented here for completeness, not as a 06.1 gap.
