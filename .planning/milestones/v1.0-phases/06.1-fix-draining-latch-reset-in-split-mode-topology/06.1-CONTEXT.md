# Phase 06.1 Context: Fix draining latch reset in split-mode topology

**Inserted after Phase 6** to close a real production-breaking bug found by
automated goal-backward verification during v1.0 milestone close
(06-VERIFICATION.md, gsd-verifier). This is the highest-severity finding
across the whole v1.0 re-verification pass.

## Diagnosed bug (no discuss-phase needed — root cause and fix location already known)

`ClientManager.isDraining()` latch is set to `true` on every EventBridge
`"draining"` event, including one published by an **engine-only** SIGTERM
(a crash-restart or independent redeploy of just the engine tier) that has
nothing to do with the gateway's own lifecycle. The ONLY place
`setDraining(false)` is called is `ClientManager.clear()`, which only runs
from `GatewayInstance.stop()` — i.e., after the *gateway itself* has already
shut down.

In `docker-compose.yml`'s split-mode topology (this project's primary
production topology, with `restart: unless-stopped` on the engine), a
single engine crash-restart permanently disables `create_room` /
`join_room` / `start_race` on an otherwise-healthy, long-running gateway for
the rest of its uptime — because the draining latch never resets.

This was already spotted in `06-REVIEW.md` as finding CR-B1, noted as "the
identical staleness problem" as a sibling `drained`-latch bug that WAS
fixed, but explicitly scoped OUT of `06-REVIEW-FIX.md` as "pre-existing,
out-of-diff-scope" — left unfixed, untested (`drain.test.ts` only asserts
the flag flips true, never that it resets), and never recorded anywhere as
an accepted risk.

## Required fix

Mirror the fix already applied to the sibling `drained` latch: make the
`draining` latch reset scoped to the draining *cycle* it belongs to, not
just to full gateway shutdown — so an independent engine-only
restart/redraining event does not permanently wedge a healthy gateway's
`ClientManager`. See the `drained`-latch fix in `06-REVIEW-FIX.md` /
`apps/gateway` for the reference pattern already used for the twin bug.

## Success criteria

- A regression test simulates an independent engine restart in split mode
  and proves `isDraining()` returns to `false` afterward (gateway keeps
  accepting `create_room`/`join_room`/`start_race`).
- The existing `drained`-latch fix pattern is followed for consistency.
- No regression in existing engine/gateway/web test suites.
