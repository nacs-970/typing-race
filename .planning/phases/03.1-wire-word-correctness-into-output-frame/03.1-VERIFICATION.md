# Phase 03.1: Wire word-correctness into output frame Verification Report

**Phase Goal (original):** Wire `aggregateWordCorrectness`/`isWordCorrect` (apps/engine/src/race/scoring.ts)
into the real race-state/wire-protocol output so per-word correctness reaches the client and is
rendered — closing the gap 03-VERIFICATION.md's Gap B identified ("No player ever sees per-word
correctness").

**Verified:** 2026-09-17
**Status:** closed via override — not a real gap, no code change needed
**Re-verification:** Yes — supersedes the initial 2026-09-16 verification (`status: gaps_found`)

## What happened

1. An initial build attempt wired `aggregateWordCorrectness` into the wire protocol
   (`cursor_update`/`rejoined_room` frames) and rendered `word-correct`/`word-incorrect` CSS classes
   in `RaceView.tsx`. A first re-verification pass (2026-09-16, superseded by this report) found that
   build's delivery was broken for the dominant forward-typing path (`excludePlayerId` excluded the
   typing player from their own broadcast) and flagged it `gaps_found`.
2. Before attempting to fix that delivery bug, a deeper read of `.planning/phases/03-race-track/03-CONTEXT.md`
   surfaced **decision D-13**, made during Phase 3's own pre-planning discussion, predating this phase:
   > "Word-correctness aggregation in server data model (not UI). Word is 'complete' only when all its
   > chars end `correct`. Used by server-side correctness stats; UI just renders per-char accents."
3. This directly contradicts the premise of the original gap-closure phase: D-13 explicitly rules out
   UI rendering as a valid consumer of `aggregateWordCorrectness`. Building that UI (even a working
   version) would have shipped a feature the project's own Phase 3 planning deliberately excluded.
4. The wire-protocol and UI-rendering work from step 1 was reverted (see commit history — the `words`
   field was removed from `cursorUpdateSchema`/`rejoinedRoomSchema`, `buildCursorUpdateFrame`/
   `buildRejoinedRoomFrame` reverted, `RaceView.tsx`/`race.ts`/`race-client.ts`/`styles.css` reverted,
   the new `apps/web/src/core/word-correctness.ts` helper deleted). The `ROOM_CLOSED` error-code
   addition, which shared `messages.ts` with this work, was preserved (it belongs to the unrelated
   04.1 gap-closure phase).
5. `03-VERIFICATION.md` was updated with a second override suggestion (Gap B), mirroring the existing
   Gap A (D-11/D-12) pattern: `aggregateWordCorrectness`/`isWordCorrect` remain unused-but-intentional,
   consistent with D-13's explicit "not UI" scoping, and no requirement or ROADMAP success criterion
   calls for a separate server-side stats consumer beyond WPM/accuracy (already fully implemented via
   different functions, per 03-VERIFICATION.md Truth #2).

## Outcome

No code change was needed to close this gap-closure phase. The original 03-VERIFICATION.md Gap B was
a verifier miss — D-13 was already in `03-CONTEXT.md` and was in fact quoted (partially) by that same
verification pass, but its "not UI" clause was not weighed heavily enough against the "used by
server-side correctness stats" clause when judging whether an override applied.

**Requirements:** `03.1-01-SUMMARY.md`'s original `requirements-completed: [REQ-05, REQ-08]` claim is
retracted — REQ-05/REQ-08 were already fully satisfied by Phase 3 itself (WPM/accuracy via
`countCorrectChars`/`countUncorrectedErrors`, not `aggregateWordCorrectness`); this phase completes
neither requirement, it resolves a verification-process gap.

**Follow-up needed:** A human should formally accept both Gap A and Gap B's override suggestions in
`03-VERIFICATION.md` (currently `accepted_by: PENDING`) so a future audit does not re-flag either.
